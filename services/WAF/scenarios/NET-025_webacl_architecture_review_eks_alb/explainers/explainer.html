Architecture

One web ACL protects both ALBs. Every change affects both applications. If their traffic is different (for example API vs browser), one web ACL per ALB makes tuning easier.

1. Rule group efficiency

What it is. Every rule consumes WCU. A web ACL includes 1,500 WCU in the base price. Above 1,500 (maximum 5,000) AWS adds a per-request charge.

How it works. WAF evaluates rules by priority. A terminating action (Allow, Block, CAPTCHA, Challenge) stops evaluation. Count doesn't. So the order decides both the cost and the result.

Recommended order

  1. Allow/Block by IP set (internal, partners, denylist). Cheap and high confidence.
  2. AWSManagedRulesAmazonIpReputationList and, if needed, AnonymousIpList.
  3. Rate-based rules (section 2).
  4. KnownBadInputs, CommonRuleSet, SQLiRuleSet, LinuxRuleSet.
  5. Expensive intelligent-threat groups (Bot Control, ATP) last, with a scope-down. They are billed per inspected request.
⚠️ Look for groups that don't match the stack. Example: LinuxRuleSet + UnixRuleSet together, or PHPRuleSet/WordPressRuleSet in front of services that don't use PHP.

2. Rate-limiting logic

What it is. A rate-based rule counts requests per aggregation key inside a window (60, 120, 300 or 600 s). When a key goes over the limit, the rule applies its action.

How it works. The default key is the source IP. You can aggregate on up to 5 keys: header, cookie, query argument, URI path, HTTP method, label namespace, JA3/JA4. A scope-down limits which requests count.

What to check

  • Real client IP. With CloudFront or another proxy in front of the ALB, the source IP is the proxy. Use FORWARDED_IP with X-Forwarded-For, or put the web ACL on CloudFront.
  • Layers. One broad rule (for example 2,000 per 5 min per IP) plus narrow rules with scope-down on /login, /otp or /api/*.
  • Identity key. For token-based APIs, aggregate on a header (Authorization or x-api-key), so a whole NAT isn't punished.
  • Precision. WAF estimates the rate and reacts after a short delay. It is not an exact counter and not a business quota.

4. False-positive risk

Walk through the tuning cycle step by step:

CommonRuleSet rules with the most false positives

  • SizeRestrictions_BODY: file uploads, large JSON.
  • CrossSiteScripting_BODY: HTML editors, rich content.
  • NoUserAgent_HEADER: health checks, machine-to-machine clients.
  • GenericRFI_QUERYARGUMENTS / GenericRFI_BODY: URLs inside parameters (callbacks, redirects).

6. Common mistakes

  • Putting new rules straight into Block, with no Count period.
  • Disabling a whole rule for one false positive on one path, instead of labels + scope-down.
  • Per-IP rate limiting behind CloudFront without FORWARDED_IP: all traffic counts as a few IPs.
  • Associating the web ACL by hand when the Ingress controller owns the ALB.
  • Assuming WAF covers the whole OWASP Top 10.
