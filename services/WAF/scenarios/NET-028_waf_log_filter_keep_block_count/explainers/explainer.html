AWS WAF: a logging filter that keeps BLOCK and COUNT

The team drops all ALLOW traffic from the WAF logs to save Firehose and S3 cost. This also drops requests that match rules in Count and end in ALLOW. The proposed filter works, but it has three traps.

Context. Media — video streaming platform. Pipeline: AWS WAF → Amazon Data Firehose → Amazon S3. Current filter: ALLOW → DROP, default behavior KEEP. Proposed filter: BLOCK | COUNT | EXCLUDED_AS_COUNT → KEEP, default behavior DROP.

1. What a logging filter is

A logging filter decides which log records AWS WAF sends to the destination. AWS WAF applies the filter before it delivers the record. A dropped record never reaches Firehose and has no ingestion or storage cost.

The filter reads two things from the record: the actions and the labels.

How it works

  1. AWS WAF evaluates the request against the web ACL rules and decides the final action.
  2. AWS WAF builds the record. The action field holds the final action (ALLOW, BLOCK, CAPTCHA or CHALLENGE). The nonTerminatingMatchingRules field lists the Count rules that matched.
  3. AWS WAF evaluates the filters from the top. The first filter that matches decides KEEP or DROP.
  4. If no filter matches, AWS WAF applies the default behavior.

An ActionCondition matches any action in the record, not only the final one. A record with final action ALLOW and one Count match meets ALLOW and also COUNT.

{
  "action": "ALLOW",                       ← final action (default action)
  "terminatingRuleId": "Default_Action",
  "nonTerminatingMatchingRules": [
    { "ruleId": "custom-geo-count", "action": "COUNT" }   ← custom rule in Count
  ],
  "ruleGroupList": [{
    "ruleGroupId": "AWS#AWSManagedRulesCommonRuleSet",
    "nonTerminatingMatchingRules": [
      { "ruleId": "NoUserAgent_HEADER", "action": "COUNT",
        "overriddenAction": "BLOCK" }          ← managed sub-rule overridden to Count
    ]
  }],
  "labels": [{ "name": "awswaf:managed:aws:core-rule-set:NoUserAgent_Header" }]
}

3. The customer's questions

Q1 — Managed sub-rule in Count that ends in the default Allow

Yes, it is kept. The record has final action ALLOW and the sub-rule appears with action COUNT. The KEEP filter has COUNT and EXCLUDED_AS_COUNT, so it matches. The default DROP applies only to records that match no filter.

The final ALLOW does not cause a drop, because the proposed configuration has no condition on ALLOW.

⚠️ Condition: delete the current ALLOW → DROP filter. If it stays above the KEEP filter, the record matches ALLOW first and is dropped (try the "Mistake" configuration in the simulator).

Note: with the current override option (RuleActionOverrides), the COUNT condition already matches managed sub-rules in Count. EXCLUDED_AS_COUNT also matches them, and the legacy ExcludedRules. Keeping both costs nothing.

Q2 — Custom rules in Count

Yes. COUNT matches every custom Count rule that matched the request, even when the final action is the default ALLOW.

One case is not kept: an Allow rule at an earlier priority (for example, an IP allowlist). That rule ends the evaluation. The later Count rules are not evaluated, so the record has no COUNT. This is web ACL evaluation, not the filter.

Q3 — Action-based (A) or label-based (B)

A. Action-basedB. Label-based
KeepsEvery request with BLOCK or any Count matchBLOCK + only the sub-rules you name
MaintenanceLow. A new Count rule is included automaticallyHigh. Each new sub-rule needs its own condition
Custom rulesIncluded without changesNeed RuleLabels to have a label
Volume controlLow. One noisy Count rule raises the costHigh. Only what you name is kept
Syntax3 conditionsFully qualified label name. No namespace, no wildcard

Performance: the filter acts on the log record, after the decision. It uses no WCU and is not in the request path. AWS documents no latency difference between A and B.

Recommendation: start with A. If one Count rule produces high volume with no tuning value, add a DROP filter with its label above it ("Hybrid" in the simulator). You keep automatic coverage and control the noise.

⚠️ For option B, use the full label name, for example awswaf:managed:aws:core-rule-set:NoUserAgent_Header. A namespace such as awswaf:managed:aws:core-rule-set: matches nothing.

Traps in the proposed configuration

  1. Filter order. The ALLOW → DROP filter must not stay above the KEEP filter.
  2. CAPTCHA and CHALLENGE. Today they are kept (default KEEP). With the proposal they are dropped. If the web ACL uses these actions, add CAPTCHA and CHALLENGE to the KEEP condition.
  3. High-volume Count rules. A Count rule that matches almost everything (label-only tagging rules, rate-based rules in Count, geo marking) makes COUNT keep almost all traffic. The cost goes back to the unfiltered level. Check CountedRequests per rule before the change.
  4. Hybrid side effect. A request with the noisy label that is also blocked matches the DROP filter first. That is why the simulator combines the label with ALLOW under MEETS_ALL: blocks are kept.

4. Cost impact

The cost difference is the volume of ALLOW requests that match at least one Count rule. Everything else is already kept today. Measure that volume with CountedRequests before the change. The per-rule value is an upper bound: a request that matches two rules counts twice.

  1. Allow before Count: in origin-playback, a host/path Allow rule ends 98.6 % of the requests before the managed groups. Those requests never carry a Count match.
  2. Count + label-based Allow: sub-rules in Count are followed by Allow exceptions, with no Block rule for the rest. Those sub-rules block nothing, and the excepted requests skip the later rate-based and IP rules.
  3. Label case: one exception rule matches NoUserAgent_HEADER; the real label is NoUserAgent_Header. It made zero allows in 14 days.

5. How to validate in the account (read-only)

1. Export the current filter. 
aws wafv2 get-logging-configuration --resource-arn <WEBACL_ARN> \
  --query 'LoggingConfiguration.LoggingFilter' --output json

Expected: one DROP filter with ActionCondition: ALLOW and DefaultBehavior: KEEP.

2. List the Count rules and the managed overrides. 
aws wafv2 get-web-acl --scope <REGIONAL|CLOUDFRONT> --region <region> \
  --name <webacl-name> --id <webacl-id> \
  --query 'WebACL.Rules[].{rule:Name,prio:Priority,action:keys(Action||`{}`)[0],overrides:Statement.ManagedRuleGroupStatement.RuleActionOverrides[].Name}' \
  --output table

Look for: rules with action = Count, Allow rules at low priority, and the overrides list. Also look for CAPTCHA or Challenge.

3. Measure the daily Count volume. 
aws cloudwatch get-metric-statistics --namespace AWS/WAFV2 \
  --metric-name CountedRequests --region <region> \
  --dimensions Name=WebACL,Value=<webacl-name> Name=Rule,Value=<rule-metric-name> Name=Region,Value=<region> \
  --start-time $(date -u -v-14d +%FT%TZ) --end-time $(date -u +%FT%TZ) \
  --period 86400 --statistics Sum --query 'Datapoints[].[Timestamp,Sum]' --output table

Repeat with AllowedRequests and BlockedRequests. For CLOUDFRONT use Region=Global and --region us-east-1. Divide Count by Allowed to get the "% ALLOW with a Count match" for the simulator.

6. How to replicate it (CLI-first)

The lab uses an ALB with a fixed response and CloudWatch Logs as the destination. The filter behaves the same with Firehose. CloudWatch Logs shows the result in minutes.

⚠️ Run everything in a lab account. The security group admits your IP only.

1. Build — Set the network variables. 
export AWS_REGION=us-east-1
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
VPC=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].VpcId' --output text)
SUBNETS=$(aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC Name=default-for-az,Values=true \
  --query 'Subnets[0:2].SubnetId' --output text)
MYIP=$(curl -s https://checkip.amazonaws.com)

Expected: echo $VPC $SUBNETS shows one VPC and two subnets.

2. Build — Create the security group and the ALB with a fixed 200 response. 
SG=$(aws ec2 create-security-group --group-name net028-alb --description net028-lab \
  --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr $MYIP/32
ALB_ARN=$(aws elbv2 create-load-balancer --name net028-alb --subnets $SUBNETS \
  --security-groups $SG --query 'LoadBalancers[0].LoadBalancerArn' --output text)
aws elbv2 wait load-balancer-available --load-balancer-arns $ALB_ARN
aws elbv2 create-listener --load-balancer-arn $ALB_ARN --protocol HTTP --port 80 \
  --default-actions 'Type=fixed-response,FixedResponseConfig={StatusCode=200,ContentType=text/plain,MessageBody=ok}'
DNS=$(aws elbv2 describe-load-balancers --load-balancer-arns $ALB_ARN \
  --query 'LoadBalancers[0].DNSName' --output text)

Expected: curl -s http://$DNS/ returns ok.

7. Common mistakes

  • Adding the KEEP filter and leaving the ALLOW → DROP filter above it.
  • Using a label namespace in LabelNameCondition. Only full names match.
  • Forgetting CAPTCHA and CHALLENGE when the default changes to DROP.
  • Estimating cost without CountedRequests. One high-volume Count rule cancels the saving.
  • Expecting Count matches behind an Allow rule. Those rules are not evaluated.
