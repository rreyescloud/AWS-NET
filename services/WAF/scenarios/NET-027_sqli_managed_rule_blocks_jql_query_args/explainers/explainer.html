AWS WAF blocks Jira JQL queries as if they were SQL injection

Users get a CloudFront 403 when they open items from a Jira dashboard. The SQLi_QUERYARGUMENTS rule in the SQLi managed rule set reads JQL/ZQL syntax as SQL. The blocks start right after a web ACL change: this is not an AWS-side change.

Summary in 4 lines
  1. At 15:21 UTC an administrator removed the Count override from SQLi_QUERYARGUMENTS (and from 5 other sub-rules).
  2. The rule went back to Block. Hourly blocks went from ~5-80 to 694 and 1,192.
  3. Each dashboard click opens /issues/?jql=project = "…" and issuetype = …. To the rule, that text looks like SQL.
  4. Fix: keep the sub-rule in Count and block on its label, except on the Jira search paths.

Press Next to follow one dashboard request. The web ACL has CLOUDFRONT scope and evaluates rules by priority, 0 to 6.

3. Why JQL looks like SQL

The SQLi_QUERYARGUMENTS sub-rule inspects the value of every query argument with LOW-sensitivity SQLi detection. JQL and ZQL have the same shape as a WHERE clause: field, operator, quoted literal and and.

The jql argument from the WAF log (sanitized). In red, the matchedData WAF recorded:
project = "Example Project" and issuetype = Test and status != Cancelled
and "Test Type" in (Spec, "Combo Script") and labels in (VAL_test) and cf[10300] = PROJ-123
The up_zqltext argument of the 3 gadgets blocked in the HAR:
project="PROJ" AND fixVersion="Client Execution" AND cycleName in ("VAL-Manual Execution")
and assignee is EMPTY and folderName in ("Priority Tests", "Net New Deliverables")

Compare: id = "1" and name = "x" is the classic tautology-based SQL injection pattern. The rule cannot know that the backend is Jira and not a database.

6. Why this is not an AWS change

  • The rule group has no pinned version (Version: null), so it follows the default version. An AWS update is possible in theory.
  • But the spike starts in the same hour as the 15:21 UpdateWebACL and ends after the 17:17 one. A version update does not switch off with an override change.
  • Before 15:21 the sub-rule was in Count, so the same JQL already matched without blocking.

7. Recommended fix: label-based exception

A rule in Count still adds its label to the request. A custom rule with a later priority can block on that label, except on the paths where JQL is legitimate.

  1. Keep SQLi_QUERYARGUMENTS in Count in RuleActionOverrides, as it is now.
  2. Add this rule with a priority number higher than the SQLi rule set (for example, 4, and shift the rest).
  3. Review labeled requests in the logs for a few days.
{
  "Name": "Block-SQLi-QueryArgs-except-tracker-search",
  "Priority": 4,
  "Statement": { "AndStatement": { "Statements": [
    { "LabelMatchStatement": { "Scope": "LABEL",
        "Key": "awswaf:managed:aws:sql-database:SQLi_QueryArguments" } },
    { "NotStatement": { "Statement": { "OrStatement": { "Statements": [
      { "ByteMatchStatement": { "FieldToMatch": { "UriPath": {} }, "PositionalConstraint": "STARTS_WITH",
          "SearchString": "/jira/issues", "TextTransformations": [{ "Priority": 0, "Type": "LOWERCASE" }] } },
      { "ByteMatchStatement": { "FieldToMatch": { "UriPath": {} }, "PositionalConstraint": "STARTS_WITH",
          "SearchString": "/jira/plugins/servlet/gadgets/", "TextTransformations": [{ "Priority": 0, "Type": "LOWERCASE" }] } },
      { "ByteMatchStatement": { "FieldToMatch": { "UriPath": {} }, "PositionalConstraint": "STARTS_WITH",
          "SearchString": "/jira/rest/", "TextTransformations": [{ "Priority": 0, "Type": "LOWERCASE" }] } }
    ] } } } }
  ] } },
  "Action": { "Block": {} },
  "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true,
    "MetricName": "Block-SQLi-QueryArgs-except-tracker-search" }
}
⚠️ The exception removes SQLi inspection of the query string on those paths. Jira parses JQL with its own parser; it does not pass it to the database as SQL. For tighter control, also require the Jira session cookie (JSESSIONID), so the exception applies only to authenticated users.

9. How to validate (commands)

Current SQLi rule set overrides

aws wafv2 get-web-acl --scope CLOUDFRONT --region us-east-1 \
  --name <web-acl-name> --id <web-acl-id> \
  --query "WebACL.Rules[?Name=='AWS-AWSManagedRulesSQLiRuleSet'].Statement.ManagedRuleGroupStatement.RuleActionOverrides"

Who changed the web ACL, and when

aws cloudtrail lookup-events --region us-east-1 \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateWebACL \
  --start-time <incident-day>T00:00:00Z \
  --query "Events[].{t:EventTime,who:Username}"

Hourly blocks for the rule set

aws cloudwatch get-metric-statistics --region us-east-1 --namespace AWS/WAFV2 \
  --metric-name BlockedRequests --statistics Sum --period 3600 \
  --dimensions Name=WebACL,Value=<web-acl-name> Name=Rule,Value=AWS-AWSManagedRulesSQLiRuleSet \
  --start-time <start> --end-time <end>

Which sub-rule and path block (CloudWatch Logs Insights)

fields @timestamp, httpRequest.uri, terminatingRuleId
| filter action = "BLOCK"
| parse @message '"terminatingRule":{"ruleId":"*"' as subrule
| stats count(*) as hits by terminatingRuleId, subrule, httpRequest.uri
| sort hits desc
| limit 50

Requests the label marks (after setting the sub-rule to Count)

fields @timestamp, httpRequest.uri, httpRequest.args
| filter @message like /SQLi_QueryArguments/
| stats count(*) as hits by httpRequest.uri
| sort hits desc

10. Common mistakes

  • Accepting "nothing changed" without checking CloudTrail. Always look for UpdateWebACL and UpdateRuleGroup in the incident window.
  • Leaving a whole sub-rule in Count forever for a false positive on one path.
  • Placing the label rule before the rule group. The label does not exist yet at that point, so the rule never matches.
  • Using ExcludedRules instead of RuleActionOverrides. Both set the rule to Count; RuleActionOverrides is the current form.
  • Debugging the origin. A 403 with X-Cache: Error from cloudfront and Server: CloudFront was generated at the edge.

12. What to tell the customer

  1. It is a false positive. JQL/ZQL has the shape of a SQL condition, so the sub-rule reads it as injection. That is why the dashboard click fails and the one-off search works.
  2. It started with a change in their web ACL. At 15:21 UTC an update removed the Count override. The metric confirms it: from under 80 to 694 and 1,192 blocks per hour. After Count was restored at 17:17, the blocks stopped.
  3. The HAR confirms it. The 3 responses with 403 come from CloudFront and never reach the origin. They are the requests with ZQL in the URL.
  4. Fix. Keep the sub-rule in Count and block on its label, except on the Jira search paths (rule in section 7).
  5. Warning. 5 other sub-rules went back to Block at 15:21 and can cause more 403s. Check in the logs which sub-rule terminates each block before changing them.

The reply gives the time of the change, not the person. The customer can verify it in their own change history.
