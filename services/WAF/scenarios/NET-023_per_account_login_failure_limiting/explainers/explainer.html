Per-account login failure limiting on a custom OAuth token endpoint

NET-023 · AWS WAF. The goal: return 429 when one account has more than 5 failed logins per minute. WAF alone can't do it. The answer is a layered design with the per-account counter in the application.

1. The requirement

Architecture: a custom OAuth 2.0 server. A Node.js Lambda sits behind API Gateway or an ALB. A REGIONAL AWS WAF web ACL protects the entry point.

Flow: the client sends POST /token with grant_type=password. Username and password are in a form-encoded body. The Lambda calls an external identity provider (IdP). The Lambda decides success or failure.

Requirement: return 429 when an account exceeds 5 failures per minute, per account, not per IP.

3. Options

Short answer: no managed AWS capability meets the exact requirement. Option D (counter in the Lambda) is the right design. WAF (A, B) reduces volume before it reaches the Lambda.

  • Confirmed: rate-based rules have mitigation lag (~50 extra requests here).
  • Observed: ATP keyed on the real source IP, not on X-Forwarded-For (label volumetric:ip:low). No password_traversal label for 30 attempts in under a minute.
  • Observed: behind API Gateway the WAF custom header arrives as-is (lab-source), with x-amzn-ErrorType: ForbiddenException.
  • Observed: a new REST stage took more than 2 minutes before WAF could associate with it.

6. Common mistakes

  • ⚠️ Lockout as DoS: an attacker can lock real users. Keep the window short and prefer step-up over long lockouts.
  • Expecting a "JSON body custom key" in a rate-based rule. It doesn't exist.
  • Using ATP response inspection on a REGIONAL web ACL. It runs only for CloudFront.
  • Expecting an exact limit from WAF. Rate-based rules and ATP have mitigation lag.
  • CAPTCHA on an API POST: the client gets 405. On an API, block with 429.
