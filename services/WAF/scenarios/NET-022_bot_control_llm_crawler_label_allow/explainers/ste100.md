# NET-022 — Explanation in ASD-STE100 (Simplified Technical English)

This text follows the ASD-STE100 rules: short sentences, one instruction in each sentence, active
voice, and approved words. Technical names (for example `CategoryAI`, `ALLOW`, `BLOCK`) are in code
format. They are names, not general words.

## 1. Description of the problem

A company has a public marketing website behind CloudFront. AWS WAF protects the website. Firewall
Manager (FMS) sends the web ACL from a security account.

The company wants LLM crawlers to read the public pages. These crawlers get an `HTTP 403` response.

There are two different causes. Each cause stops a different type of crawler.

## 2. How AWS WAF examines a request

AWS WAF examines the rules of the web ACL in a sequence. The sequence starts at the top.

A rule can add labels to the request. A label is a tag that a rule after it can read.

A rule with the action `Count` adds its labels. Then the request goes to the next rule.

A rule with the action `BLOCK` or `ALLOW` stops the sequence. AWS WAF does not examine the
remaining rules.

Bot Control is a managed rule group. It examines the User-Agent and other data. It adds labels that
identify the type of bot.

## 3. Cause A: Bot Control does not know the crawler

The crawler in this case has the User-Agent `ExampleAIBot/1.0`.

Bot Control does not have a name or a category for this User-Agent. Thus, it adds only one label:
`signal:non_browser_user_agent`.

The rule `SignalNonBrowserUserAgent` is in `Count`. The request goes to the next rules.

The last rule group has the name `<allow_seo_crawler_ua>`. The name tells you that it allows
traffic. This is not correct. The action of the rule is `BLOCK`.

The rule blocks a request when the two conditions that follow are true:

- The request has the label `signal:non_browser_user_agent`.
- The User-Agent is not one specified string of an SEO crawler.

The LLM crawler agrees with the two conditions. Thus, the rule blocks it.

No rule that uses Bot Control labels can let this crawler through. The crawler has no AI label.

## 4. Cause B: `CategoryAI` blocks AI bots that Bot Control knows

Some LLM crawlers have a name in Bot Control. Bot Control adds the labels `bot:category:ai`,
`bot:name:<known-ai-bot>` and `bot:verified` to them.

The rule `CategoryAI` is in `BLOCK`. This rule blocks verified AI bots and unverified AI bots. The
other category rules of Bot Control do not block verified bots.

Thus, these crawlers stop at Bot Control. They do not go to the last rule group.

## 5. Procedure to find the cause

1. Get two or three blocked requests from the WAF logs.
2. Find the `terminatingRuleId` in each log entry.
3. If the terminating rule is the last custom rule group, the cause is Cause A.
4. If the terminating rule is `CategoryAI`, the cause is Cause B.
5. Read the `labels` of each request.
6. If you see only `signal:non_browser_user_agent`, Bot Control does not know the crawler.
7. Get the `availableLabels` of the Bot Control version that you use.
8. Make sure that the crawler name is in this list. If it is not in the list, Bot Control does not
   classify the crawler.
9. Read the action and the statement of each custom rule group.

**CAUTION:** Do not use the name of a rule group to find its action. The name can be incorrect.
Read the action in the rule definition.

## 6. Procedure to repair the problem

### 6.1 Change only `CategoryAI`

1. Open the FMS policy.
2. Find the Bot Control rule group.
3. Set the action of `CategoryAI` to `Count`.
4. Do not change the other category rules. They must stay in `BLOCK`.

`CategoryAI` continues to add its labels. It does not stop the request.

**WARNING:** Do not set all of Bot Control to `Count`. If you do this, Bot Control does not stop
bad bots on the website.

### 6.2 Replace the last rule group

Put these four rules in the last rule group, in this sequence:

- **P0 `ALLOW`:** the host is the marketing website. The method is `GET` or `HEAD`. The request
  has `bot:category:ai` and a verified label.
- **P1 `ALLOW`:** the host is the marketing website. The method is `GET` or `HEAD`. The User-Agent
  contains `ExampleAIBot`. The source IP address is in the IP set of the vendor.
- **P2 `BLOCK`:** the request has `bot:category:ai`.
- **P3 `BLOCK`:** the request has `signal:non_browser_user_agent` and does not have
  `bot:name:<seo-crawler>`.

P0 lets all verified AI crawlers through. This includes new crawlers in the future.

P1 is a temporary rule for the crawler that Bot Control does not know.

**WARNING:** Do not use the User-Agent alone in P1. Other persons can send the same User-Agent. Use
the IP set of the vendor with the User-Agent.

P2 blocks the AI requests that P0 did not let through. Examples are unverified AI bots, and AI bots
on the portal.

P3 replaces the old rule. It uses the label of the SEO crawler, not a fixed User-Agent string.

### 6.3 Do a test before you enforce the rules

1. Set the four new rules to `Count`.
2. Wait 24 to 48 hours.
3. Examine the labels and the terminating rules in the logs.
4. Make sure that each request gets the correct result.
5. Set each rule to its real action.

### 6.4 Permanent repair for Cause A

1. Send a request to AWS Support.
2. Ask AWS to add the crawler to Bot Control.
3. When Bot Control verifies the crawler, P0 lets it through.
4. Remove P1.

## 7. Why the last rule group is in the post-process position

The last rule group is after the other managed rule groups. When a request gets to it, IP
reputation, CRS, SQLi and geo rules have examined the request.

An `ALLOW` in this position does not skip these rules.

**CAUTION:** If you put an `ALLOW` at the start of the web ACL, AWS WAF does not examine the request
with the other rules. An `ALLOW` at the start means "do not examine". It does not mean "trust".

## 8. Lesson

The name of the rule group said "allow". The action was `BLOCK`. The rule group was in the last
position, where persons do not look first.

Always read the action and the statement of a rule. Do not trust its name.
