# AWS Network Firewall - Logging and Monitoring

## Log Types

AWS Network Firewall supports two types of logs:

### FLOW Logs
- Record network flow metadata for **all** traffic passing through the firewall
- Similar to VPC Flow Logs but specific to firewall-processed traffic
- Include: source/destination IP, ports, protocol, action taken, bytes transferred
- Useful for: traffic analysis, baseline establishment, audit compliance
- Generated regardless of rule match

### ALERT Logs
- Generated only when traffic **matches a stateful rule** with an `alert` or `drop` action
- Include: rule details (SID, message, classification), Suricata signature info, full packet metadata
- Useful for: security monitoring, incident response, rule tuning
- Only generated by stateful rules (stateless rules do NOT produce ALERT logs)

---

## Log Destinations

Network Firewall can send logs to three destinations (can use multiple simultaneously):

### 1. Amazon CloudWatch Logs
- Real-time log delivery
- Integration with CloudWatch Insights for querying
- Metric filters for alerting
- Best for: operational monitoring, real-time alerting, short-term analysis
- Reference: [Sending NF logs to CloudWatch Logs](https://docs.aws.amazon.com/network-firewall/latest/developerguide/logging-cw-logs.html)

### 2. Amazon S3
- Cost-effective long-term storage
- Best for: compliance archival, long-term retention (7+ years for financial sector)
- Integration with Athena for ad-hoc queries
- Reference: [Sending NF logs to S3](https://docs.aws.amazon.com/network-firewall/latest/developerguide/logging-s3.html)

### 3. Amazon Kinesis Data Firehose
- Streaming delivery to downstream consumers
- Best for: SIEM integration, real-time analytics, Splunk/Datadog/OpenSearch delivery
- Buffering and transformation capabilities
- Reference: [Sending NF logs to Kinesis Firehose](https://docs.aws.amazon.com/network-firewall/latest/developerguide/logging-kinesis.html)

## CloudWatch Resource Policy for Log Delivery

Network Firewall uses the `delivery.logs.amazonaws.com` service principal to deliver logs to CloudWatch. A CloudWatch Logs resource policy must grant this service permission.

### Required Resource Policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AWSNetworkFirewallLogging",
      "Effect": "Allow",
      "Principal": {
        "Service": "delivery.logs.amazonaws.com"
      },
      "Action": [
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:<region>:<account-id>:log-group:<log-group-name>:*",
      "Condition": {
        "StringEquals": {
          "aws:SourceAccount": "<account-id>"
        },
        "ArnLike": {
          "aws:SourceArn": "arn:aws:logs:<region>:<account-id>:*"
        }
      }
    }
  ]
}
```

### Common Resource Policy Issues

- CloudWatch Logs has a **limit of 10 resource policies per region**
- Each policy has a **5120 character limit**
- Consolidate policies when possible
- If the limit is reached, combine multiple log group ARNs into a single policy

## CloudWatch Metrics

Key metrics available under the `AWS/NetworkFirewall` namespace:

| Metric | Description |
|--------|-------------|
| `Packets` | Total packets processed |
| `DroppedPackets` | Packets dropped by stateful rules |
| `PassedPackets` | Packets passed by stateful rules |
| `ReceivedPackets` | Packets received at the firewall endpoint |
| `StreamExceptionPolicyPackets` | Packets handled by stream exception policy |

Note: DroppedPackets showing non-zero values 24x7 is **normal** for blocked traffic (this is the firewall working as intended).

## Troubleshooting Checklist: Logging Not Working

### 1. Verify Logging Configuration
- [ ] Logging enabled on the firewall?
- [ ] Log types configured (FLOW, ALERT, or both)?
- [ ] Log destination correct (CloudWatch, S3, Kinesis)?
- [ ] Log group/bucket/stream name correct?

### 2. Verify Log Group (CloudWatch)
- [ ] Log group exists in CloudWatch?
- [ ] Naming convention correct?
- [ ] Retention policy configured?
- [ ] Log streams present (check if any have been created)?

### 3. Verify CloudWatch Resource Policy
- [ ] Resource policy exists?
- [ ] Service principal correct (`delivery.logs.amazonaws.com`)?
- [ ] Actions include `CreateLogStream` AND `PutLogEvents`?
- [ ] Resource ARN matches the log group ARN?
- [ ] Conditions appropriate (SourceAccount, SourceArn)?
- [ ] Not hitting the 10 resource policy limit per region?

### 4. Verify Traffic Is Actually Reaching the Firewall
- [ ] CloudWatch metrics show `Packets > 0`?
- [ ] Route tables direct traffic to firewall endpoints?
- [ ] VPC Flow Logs show traffic on firewall endpoint ENIs?
- [ ] Firewall endpoints in state `READY`?

### 5. Verify Firewall Policy and Rules
- [ ] Rules with `alert` or `drop` action configured? (required for ALERT logs)
- [ ] `StatefulDefaultActions` includes `aws:alert_established` or `aws:alert_strict`?
- [ ] Rule groups associated correctly to the policy?
- [ ] Rule evaluation order correct (strict vs action order)?

### 6. Verify Permissions
- [ ] Service-linked role exists (`AWSServiceRoleForNetworkFirewall`)?
- [ ] IAM permissions correct for the log destination?
- [ ] KMS key permissions (if logs are encrypted)?

### 7. Manual Test
- [ ] Create a specific test rule with `alert` action
- [ ] Generate traffic that matches the rule
- [ ] Wait **5-10 minutes** (log delivery has latency)
- [ ] Verify logs appear in destination
- [ ] If FLOW logs appear but ALERT logs do not, the issue is rule configuration

## Common Logging Errors

### "Given logging configuration changes a destination type for a log type"

This error occurs when you try to change the destination type (e.g., from CloudWatch to S3) for an existing log type. You must:
1. Remove the existing logging configuration for that log type
2. Then add the new destination type

### Logs Appear Empty or Missing

- Confirm traffic is routed through the firewall (check VPC Flow Logs on the firewall ENI)
- For ALERT logs: ensure rules actually match traffic (use a broad test rule)
- For FLOW logs: any traffic through the firewall should generate logs
- Check that the firewall endpoint is in READY state

## Autoscaling and Session State

- NFW is a managed service - no customer notification mechanism for scaling events
- Session state sharing is enabled - synchronizes flow data across firewall instances in the same AZ
- This eliminates midstream flow drops during scale-in, patching, or maintenance
- Scaling events are transparent to customers

## Logging Configuration

- Can be updated after creation: [Updating Logging Configuration](https://docs.aws.amazon.com/network-firewall/latest/developerguide/firewall-update-logging-configuration.html)
- Supports server-side encryption with KMS
- Can send FLOW and ALERT logs to different destinations
