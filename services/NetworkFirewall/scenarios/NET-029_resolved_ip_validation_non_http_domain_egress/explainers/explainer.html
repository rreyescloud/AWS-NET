Network Firewall: Route 53 resolved IP validation

Network Firewall checks that a connection's destination IP came from a DNS answer of your VPC's Route 53 Resolver. This blocks SNI/Host spoofing and applies domain rules to any protocol (SSH, SFTP, generic TCP).

Scenario NET-029 · Sources: the What's New announcement (2026-10-21) and the AWS Network Firewall Developer Guide / API Reference. No additional charge. Available in the commercial Regions that have Network Firewall and Route 53 Resolver DNS Firewall.

1. The problem it solves

A standard domain rule reads the name that the client asserts. For TLS it reads the SNI. For HTTP it reads the Host header. The client controls both fields.

A malicious process can send SNI: allowed.example.com and connect to the IP of its command-and-control server. The domain rule sees an allowed name and passes the connection.

Classic rule (TLS_SNI) 
SNI   = allowed.example.com   ✔ in allowlist
IP    = 203.0.113.99          (not checked)
→ PASS — spoofing succeeds
With resolved IP validation 
SNI   = allowed.example.com   ✔ in allowlist
IP    = 203.0.113.99
Did the Resolver return this IP? ✘
→ DROP / REJECT / ALERT

The second effect matters just as much. Many protocols carry no domain name in the traffic: SSH, SFTP, databases, proprietary TCP. Before, you could filter them only by IP or CIDR. Now the firewall knows which domain each IP was resolved for, so you can write "allow SSH only to .partner.example.com".

Think of it this way. The policy level is an integrity control: "never connect to an IP that didn't come from DNS". The rule level is a policy control: "which domains you may reach, over any protocol".

4. Policy settings

The API structure is Route53ResolvedIPValidation and belongs to the firewall policy. It has three required fields and two optional ones.

Action required

What the firewall does with a connection that fails validation.

  • ALERT: tags the connection in the flow logs and doesn't block it. Requires logging. Use it to measure impact before you block.
  • DROP: blocks the connection silently. The client waits until it times out.
  • REJECT: blocks and sends a TCP RST. On non-TCP traffic (UDP, ICMP) it drops.

DNSFirewallRuleGroupId required

The ID of a Route 53 Resolver DNS Firewall rule group, in the format ^rslvr-frg-[0-9a-f]+$.

  • This field defines which VPCs count. An IP counts as resolved only if the Resolver returned it in a VPC associated with this rule group.
  • Associate the rule group with every VPC whose traffic goes through the firewall.
  • Each policy has one managed association with DNS Firewall. When you change the ID, the firewall swaps the association asynchronously. During the swap it rejects other changes to this block. Wait for the policy to return to ACTIVE.
  • The rule group can be empty. It doesn't have to block anything to work as the anchor. You can also reuse one that already filters DNS.

DNSExpiryExceptionPolicy required

What to do when the cache entry has expired and traffic to that IP keeps arriving. Examples: an SSH session of several hours, or a client that caches DNS longer than the TTL.

  • CONTINUE: treats the expired entry as valid. This is the least disruptive option.
  • DROP / REJECT: blocks. It is stricter and can break clients with their own DNS cache (JVM, persistent connections).

The firewall keeps each entry longer than the TTL. A short TTL on its own doesn't break connections.

SourceIPRanges optional

The sources to validate. Up to 100 IPv4/IPv6 addresses or CIDRs.

  • Field omitted: validates the CIDRs of the firewall VPC and of any additional VPCs attached to the firewall.
  • Empty list []: validates no source. That isn't the same as omitting the field.
  • It affects the policy level only. Resolved-domain rules evaluate regardless.

BypassDestinationValidationIPRanges optional

Destinations exempt from the policy-level check. Up to 100 IPv4/IPv6 addresses or CIDRs. Use it for legitimate destinations without DNS: fixed partner IPs, NTP by IP, on-premises appliances.

It affects the policy level only. An aws_route_53_resolved_domain rule still evaluates those destinations.

Example block

{
  "Action": "ALERT",
  "DNSFirewallRuleGroupId": "rslvr-frg-0123456789abcdef",
  "DNSExpiryExceptionPolicy": "CONTINUE",
  "SourceIPRanges": [
    { "AddressDefinition": "10.0.0.0/16" }
  ],
  "BypassDestinationValidationIPRanges": [
    { "AddressDefinition": "198.51.100.0/24" }
  ]
}

Which changes restart the stateful engine

ChangeRestart?
Enable or disable validationMay restart
Change DNSFirewallRuleGroupIdMay restart (and the swap is asynchronous)
Action, DNSExpiryExceptionPolicy, SourceIPRanges, BypassDestinationValidationIPRangesNo
⚠️ If the engine restarts, the firewall handles open connections according to the stream exception policy. With DROP or REJECT, long sessions are cut. Enable validation in a maintenance window.

When you remove the block from the policy, the firewall removes the managed DNS Firewall association and validation stops applying.

5. Resolved-domain rules

There are three ways to write them. All three need the policy level enabled.

a) Domain list

Add AWS_ROUTE_53_RESOLVED_DOMAIN to the target types, alongside TLS_SNI and HTTP_HOST or instead of them.

{
  "RulesSource": {
    "RulesSourceList": {
      "Targets": [".partner.example.com", "api.example.com"],
      "TargetTypes": ["AWS_ROUTE_53_RESOLVED_DOMAIN"],
      "GeneratedRulesType": "ALLOWLIST"
    }
  }
}

With only AWS_ROUTE_53_RESOLVED_DOMAIN, the allowlist applies to all IP traffic, not only HTTP/HTTPS. Combining it with TLS_SNI/HTTP_HOST follows the rules in the "Stateful domain list rule groups" guide. Read them before you mix target types.

b) Suricata

GoalRule
Drop one exact domaindrop ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:"example.com"; flow:to_server, established; sid:1;)
Domain and subdomains (leading dot)pass ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:".example.com"; flow:to_server, established; sid:2;)
Reject (requires tcp)reject tcp $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:".ads.example.com"; flow:to_server, established; sid:3;)
Several domains (OR)drop ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:"api.example.com,cdn.example.com"; flow:to_server, established; sid:4;)
Anti-spoofing: SNI and resolution must matchpass tls $HOME_NET any -> $EXTERNAL_NET any (tls.sni; content:"example.com"; nocase; startswith; endswith; aws_route_53_resolved_domain:"example.com"; flow:to_server, established; sid:5;)

Recommended pattern: SSH/SFTP to one partner only

pass tcp $HOME_NET any -> $EXTERNAL_NET 22 (aws_route_53_resolved_domain:".partner.example.com"; flow:to_server, established; sid:100;)
drop tcp $HOME_NET any -> $EXTERNAL_NET 22 (flow:to_server, established; sid:101;)

c) Standard stateful rule

In the API, add a RuleOption with Keyword: aws_route_53_resolved_domain and a single setting in double quotes, for example "example.com,cdn.example.com". In the console, choose Standard stateful rule → Domain filtering. The console writes the keyword for you.

Syntax rules:
  • Put the domain in double quotes.
  • Use one aws_route_53_resolved_domain keyword per rule. For several domains, separate them with commas inside the value.
  • The wildcard is .example.com, not *.example.com.
  • reject doesn't work with the ip protocol. Use tcp.

    8. Operations and rollout

    1. Enable the firewall's flow and alert logs. ALERT leaves no trace without logs.
    2. Create or reuse a DNS Firewall rule group and associate it with every source VPC.
    3. Enable validation with Action=ALERT in a maintenance window, because it may restart the engine.
    4. Observe for 1-2 weeks. List the destinations that fail: fixed IPs, on-premises DNS, clients with their own DNS.
    5. Fix them with bypass ranges, new associations or client changes.
    6. Switch to DROP or REJECT. This change doesn't restart the engine.
    7. Add the resolved-domain rules for SSH/SFTP and the TLS anti-spoofing rule.
    REJECT gives the client fast, clear failures (connection reset). DROP gives timeouts, which take longer to diagnose. For internal corporate traffic, REJECT is usually the better choice.

    11. What the documentation doesn't say

    Verify these points in the lab before you state them to anyone:

    • The exact key name inside FirewallPolicy. The type is Route53ResolvedIPValidation. Check with aws network-firewall update-firewall-policy help.
    • The exact flow log field that tags a connection with ALERT.
    • The order between the policy check and the rule groups.
    • With CNAMEs: does the rule match the queried name, the CNAME target, or both?
    • How long the cache keeps each entry. The documentation only says "longer than the TTL".
    • Whether queries forwarded through an inbound endpoint from on premises count as resolved.
    • The behavior with several IPs per domain and with AAAA answers.
